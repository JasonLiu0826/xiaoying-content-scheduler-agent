# 方案与技术取舍

## 架构

`CLI → 输入校验 → Agent 循环 → 模型适配器 → 工具白名单 → 业务校验 → SQLite 草稿库`

输入和规则不可被模型修改。Agent 只根据模型生成的工具调用执行动作，将结构化工具结果写回消息，再由模型选择下一步。模型可以调用结束工具，但最终报告从业务账本生成，不能直接相信模型的自然语言成功声明。

工具计划为 `read_material`、`check_rules`、`query_slots`、`save_draft`、`finish`。每个工具包含简短 `reason`，只记录可供评审的动作依据，不采集或要求内部思维过程。业务工具返回 `{ok, data}` 或 `{ok:false, error:{code,message,retryable}}`。

## 确认与冲突

请求的 `requestedAt` 始终保留。原时间不可用时，模型查询候选时间并选择建议；缺少匹配的人工确认则保存待确认草稿。已确认草稿以数据库唯一约束占用渠道/时段，待确认建议不占位。保存工具在事务内重新审核、检查时段和权限，避免依赖过期的查询结果。

同一请求 ID 对应规范化输入摘要，重复提交读取原草稿；不同输入复用相同 ID 返回 `IDEMPOTENCY_CONFLICT`。确认属于业务状态更新，不新增第二份草稿；再次确认时重新查询冲突。

## 状态与事实来源

审核结果、查到的时间、保存回执及工具失败进入运行账本；最终结构化结果由账本和持久化回执推导。`completed` 仅在全部请求项按原要求或已授权修改保存成功时成立；`needs_confirmation`、`needs_input`、`blocked`、`failed`、`incomplete` 分别表达待确认、缺资料、阻断、失败和未完成。

## 技术选择

- TypeScript + Node.js 22.18+：沿用候选人已有工程经验，CLI 便于复制运行。
- 原生工具调用循环：流程短，动作、上限与状态可直接审查；不引入大型 Agent 框架。
- SQLite（Node 内置 `node:sqlite`）：事务和唯一约束解决保存一致性与防重复，无外部数据库部署。该 API 在 Node 22 为实验性，锁定最低运行版本并使用 CI 验证。
- OpenAI 兼容 Chat Completions：非流式调用便于完整解析工具参数，减少流式提前执行的复杂度。
- 确定性 Mock：供离线演示与故障注入，明确不作为真实模型决策证据。

参考个人项目 `JasonLiu0826/ackem` 中 AckemCode 的工具消息协议、模型调用/错误分类和事件回传方式。保持精简的独立实现，不迁入桌面 UI、MCP、LSP、沙箱、记忆、Hooks、多 Agent 或通用文件/命令执行能力。实际复制或改写的范围在 `04-ai-usage.md` 和后续 PR 中记录，不把历史成果描述为本次新增。
